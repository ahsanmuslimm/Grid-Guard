Final Result
What GridGuard Looks Like When Complete
The finished product judges will see, interact with, and score.

GridGuard is a live, hosted web application accessible via a public URL on Google Cloud Run. When a judge opens it, they see a real-time energy infrastructure security operations center. The AI agent is running, watching for threats, and reacting — all transparently traced in Arize Phoenix. Every decision the agent makes is visible, explainable, and auditable.

🖥️
Live Threat Dashboard
Real-time map of energy grid nodes. Active threat indicators. Agent decision timeline. Color-coded severity levels updating live via WebSocket.
🤖
Autonomous Agent Pipeline
6-step pipeline running continuously: detect anomaly → investigate threat → classify severity → approve/execute response → generate report → log to Phoenix.
🧠
Arize Phoenix Observatory
Full trace of every AI decision. Hallucination detection firing. Response quality scores. Session replay. All visible in Phoenix dashboard linked from the app.
🔐
Human Approval Gate
Critical threats pause the agent and surface an approval card. Operator sees the full AI reasoning before choosing: Approve, Reject, or Escalate.
📋
Incident Report Generator
Every resolved incident produces a plain-English report: what happened, what the agent did, why, what CVEs were involved, outcome, and agent confidence score.
⚡
Attack Scenario Injector
Demo control panel to inject 4 attack types live during the demo video: ransomware, unauthorized access, DDoS, data exfiltration — triggering the full pipeline on demand.

Build Sequence
Every Phase — What To Build + What To Expect
Sequential. Do not skip phases. Every phase produces a verifiable output before moving forward.
Phase 01 — Prerequisites
Install All Tools Locally
What To Build
  • Python 3.11 — core runtime for all agent code
  • Node.js 20+ — mandatory for Arize Phoenix MCP server (runs via npx)
  • gcloud CLI — deploy to GCP, manage APIs, create secrets
  • Docker Desktop — local Phoenix deployment + container testing
  • GitHub repo (public) — named "gridguard", Apache 2.0 license added immediately
  • .gitignore — credentials/, .env, venv/ all excluded from day one
What To Expect At End of Phase
  • Running python3 --version returns 3.11.x
  • Running node --version returns v20.x
  • Running gcloud --version returns SDK version
  • GitHub repo is public with LICENSE file visible in About section
All 4 CLI tools verified working. Public repo created. Zero code written yet — only environment ready.
Phase 02 — GCP Project Setup
Configure Google Cloud From Scratch
What To Build
  • GCP Project named gridguard-agent-2026 — free trial activated
  • 9 APIs enabled — aiplatform, run, cloudbuild, secretmanager, artifactregistry, resourcemanager, iam, logging, monitoring
  • Service account gridguard-sa with aiplatform.user + secretmanager.secretAccessor + run.invoker roles
  • Credentials JSON downloaded to credentials/gcp-key.json (gitignored)
  • Application default credentials configured for local SDK access
  • Billing alert at $50 — prevents surprise charges during development

What To Expect At End of Phase
  • gcloud config get-value project returns gridguard-agent-2026
  • Vertex AI SDK connects: vertexai.init() runs without error
  • All 9 APIs show as enabled in GCP Console → APIs & Services
  • Billing alert configured and visible in GCP Console → Billing
GCP project fully configured. All APIs enabled. Service account ready. Zero code deployed yet — only infrastructure ready.
Phase 03 — Python Environment + Project Structure
Build The Codebase Skeleton
What To Build
  • Virtual environment venv/ with Python 3.11 isolated
  • requirements.txt with 20+ packages — ADK, Phoenix, FastAPI, instrumentation, data tools
  • Complete folder structure — agents/, tools/, simulator/, playbooks/, observability/, frontend/, deploy/
  • __init__.py files in every Python package folder
  • .env file with all environment variable slots (no real keys yet)
  • .env.example committed to repo as template for judges
What To Expect At End of Phase
  • All packages install without errors: pip install -r requirements.txt
  • import google.adk works inside venv
  • import phoenix works inside venv
  • Full folder structure visible with all directories and __init__ files present
Complete project skeleton ready. All imports resolve. Ready to write actual code into empty files.
Phase 04 — Google ADK Multi-Agent System
Build The 3 Sub-Agents + Orchestrator
What To Build
  • Detection Agent — LlmAgent with Gemini 2.0 Flash, 4 SCADA monitoring tools, output_key="detection_result" writing to session state
  • Investigation Agent — LlmAgent reading {detection_result} from state, MITRE + CVE tool calls, output_key="investigation_result"
  • Response Agent — LlmAgent reading both upstream results, playbook execution, human approval gate logic, report generation
  • SequentialAgent Orchestrator — chains all 3 sub-agents in detection → investigation → response order
  • InMemorySessionService + Runner — local test harness for pipeline execution
  • ADK Web UI test — adk web command to inspect agent visually
What To Expect At End of Phase
  • Running the pipeline locally produces: Detection result → Investigation result → Response result in sequence
  • ADK Web UI at localhost:8000 shows agent hierarchy: orchestrator → 3 sub-agents
  • Session state correctly passes data between sub-agents via output_key
  • No import errors, no runtime crashes on a basic "no anomaly" run
Full agent pipeline running locally. 3 sub-agents chained. Data flows correctly through session state. No Arize integration yet — agents run blind.
Phase 05 — Arize Phoenix Integration
Wire Observability Into Every Agent Decision
What To Build
  • Arize Phoenix Cloud account — free tier, project named "gridguard", API key retrieved
  • Phoenix MCP server config — mcp_config.json with npx command, baseUrl, apiKey
  • phoenix_setup.py — registers Phoenix as OTel tracer provider, instruments VertexAI and GoogleGenAI automatically
  • Custom spans in every tool — each tool function wrapped with tracer.start_as_current_span() and meaningful attributes
  • Hallucination evaluator — Phoenix HallucinationEvaluator configured with Gemini eval model
  • Response quality evaluator — RelevanceEvaluator scoring playbook appropriateness
  • Session replay — enabled via Phoenix dataset logging per incident
What To Expect At End of Phase
  • Phoenix dashboard at app.phoenix.arize.com shows live traces for every agent run
  • Each agent step appears as a named span with attributes (input, output, confidence, latency)
  • Hallucination evaluator fires and flags at least one test scenario correctly
  • Response quality score appears on completed incident spans
  • Session replay reconstructable from Phoenix for any past incident
Every agent decision is now fully observable. Arize Phoenix shows complete traces. Hallucination detection active. This is your biggest competitive advantage — it must work flawlessly.
Phase 06 — Data Layer
SCADA Simulator + Threat Intelligence APIs
What To Build
  • SCADA Simulator — SCADASimulator class generating realistic telemetry: voltage (230V ±5%), frequency (50Hz ±0.2Hz), current, access logs, command logs
  • 4 Attack Injectors — ransomware (voltage spike + encrypt commands), unauthorized_access (foreign IP + privilege escalation), ddos (packet flood patterns), data_exfiltration (large outbound + unusual read patterns)
  • MITRE ATT&CK ICS connector — fetches from public MITRE STIX JSON, filters ICS-specific techniques, maps anomaly types to MITRE tactic categories
  • NVD CVE connector — queries NIST NVD API v2.0 for SCADA/ICS CVEs matching attack type, returns real CVE IDs with CVSS scores
  • 4 Playbook JSON files — ransomware.json, unauthorized_access.json, ddos.json, data_exfiltration.json with action sequences and escalation paths
  • Playbook executor — reads playbook JSON, executes action list, logs each action to Phoenix trace
What To Expect At End of Phase
  • Simulator generates 10 normal readings per second without errors
  • Injecting "ransomware" scenario produces clearly anomalous telemetry values
  • MITRE lookup returns real technique objects for each attack type
  • NVD API returns real CVE IDs (e.g. CVE-2023-XXXX) for SCADA queries
  • All 4 playbooks execute without errors and log action sequences
Data layer complete. Agent now has real tools to call during investigation. End-to-end pipeline runs on injected attack: detect → MITRE lookup → CVE lookup → playbook execute.
Phase 07 — GCP Secret Manager
Secure All API Keys
What To Build
  • PHOENIX_API_KEY secret — stored in Secret Manager via gcloud command
  • NVD_API_KEY secret — stored in Secret Manager
  • get_secret() utility function — SecretManagerServiceClient wrapper used in all modules instead of os.getenv()
  • Replace all .env reads in production code with get_secret() calls
  • Verify zero hardcoded credentials — grep codebase for any raw API key strings
What To Expect At End of Phase
  • gcloud secrets list shows PHOENIX_API_KEY and NVD_API_KEY
  • get_secret("PHOENIX_API_KEY") returns correct key value at runtime
  • Full grep of codebase returns zero hardcoded key strings
  • Application still runs correctly after replacing .env reads with Secret Manager calls
All secrets secured. Zero credentials in codebase or environment files. Production-grade security posture that judges will notice during code review.

  • POST /api/approve/{id} — human approval signal to waiting response agent

What To Expect At End of Phase
  • Dashboard loads at localhost:8080 within 2 seconds
  • Threat map updates live — clicking "Inject Ransomware" makes a node go red within 3 seconds
  • Decision timeline shows agent actions appearing in real time
  • Human approval modal fires and pauses pipeline for CRITICAL scenarios
  • Incident reports appear in list after each resolved incident

Success Definition
Exactly What A Winning Submission Looks Like
The non-negotiable bar. If all of these are true, you win or place in Arize track.
MUST HAVE 01
Agent Executes Actions, Not Just Answers
Every agent response triggers a real tool call. The system isolates nodes, blocks IPs, generates reports. It does not just reply with text. This is the core hackathon requirement: move beyond chat.
Non-Negotiable
MUST HAVE 02
Arize Integration Is Deep, Not Surface
Phoenix traces show every sub-agent span with meaningful attributes. Hallucination evaluator is configured and fires on at least one demo scenario. Judges from Arize will click through the Phoenix dashboard.
Non-Negotiable
MUST HAVE 03
Human Approval Gate Works Live In Demo
The CRITICAL threat scenario must visibly pause the agent, surface the approval card with AI reasoning visible, and wait for human input before proceeding. This is the safety demonstration judges want to see.
Non-Negotiable
MUST HAVE 04
Demo Works Flawlessly On Public URL
The Cloud Run URL loads fast, the demo cycle completes without errors, and the system works from any device. Test from a completely different network before recording. A broken demo loses immediately.
Non-Negotiable
MUST HAVE 05
Real Data — Not Mocked Responses
MITRE ATT&CK lookup returns real technique objects. NVD CVE query returns real CVE IDs. SCADA telemetry looks realistic. Judges from Arize know what fabricated data looks like. Do not mock the intelligence layer.
Non-Negotiable
MUST HAVE 06
GitHub Repo Is Clean and Complete
Public repo. Apache 2.0 license in About section. README with architecture diagram, setup instructions, demo video link, live URL. Judges clone repos and attempt to run them. Make it work on the first try.
Non-Negotiable
The One Sentence That Defines Winning When the Arize judge opens Phoenix after your demo and sees every decision traced, a hallucination flagged, and a quality score attached — that is the moment you separate from every other team in the track.
The One Thing That Loses A broken demo. Every requirement above could be met perfectly but if the demo crashes during recording or the Cloud Run URL is down when judges visit — you are out. Rehearse 5 times. Set min-instances=1. Test from external network.
